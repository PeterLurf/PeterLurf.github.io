# Academic website

A personal academic site in plain HTML, CSS and JavaScript: a homepage, a blog and interactive experiments. One small Python script builds the blog; everything else is hand-written files. Preview it through a local server (below).

## Files

| Path | What it is |
|---|---|
| `index.html` | The homepage. Search for `EDIT:` to find what's left to fill in. |
| `style.css` | The look for every page. Colors are at the top under `:root`. |
| `posts/` | **Your blog posts, in Markdown.** This is where you write. Empty for now (`.gitkeep` only keeps the folder on GitHub). |
| `build.py` | Turns `posts/` into pages, updates the post lists and the feed, and syncs the sidebar. |
| `templates/` | `side.html` (the sidebar on every page) and `post.html` (the layout of a post). |
| `blog/` | Generated by `build.py`, except `blog/index.html`'s surrounding page. Don't edit post pages by hand. |
| `experiments/` | One folder per experiment, plus the index page. Empty for now. |
| `feed.xml` | Generated Atom feed, so people can subscribe to the blog. |
| `sitemap.xml` | Generated list of every page, for search engines. |
| `robots.txt` | Points search engines to the sitemap and keeps them out of `options/`. |
| `.github/workflows/deploy.yml` | Tells GitHub to run `build.py` and publish the site on every change (see Publishing). |
| `404.html` | What GitHub Pages shows for a link that doesn't exist. |
| `images/` | `profile.jpg` (the photo, also the link-preview image) and `apple-touch-icon.png` (the icon when someone saves the site to a phone's home screen). |
| `options/` | Design mockups. Delete the folder before publishing if you don't want them online. |

Parked outside the site:
- `../lavender-build/`: the previous lavender design.
- `../figure-first-build/`: option E built out as a full site.
- `../interp-archive/`: the earlier GPT-2 views that ran on the homepage itself.
- `../interp-archive/removed-samples/`: the sample logit lens post and experiment (with `lens_trace.py`, which made its data). Copy them back to reuse them.

## What build.py keeps up to date for you

- **Empty sections stay hidden.** The Blog and Experiments links only appear in the sidebar once there's a post or an experiment; with neither, the nav is left out (the photo links home). Empty sections are also left out of the sitemap. Your first post brings the Blog link back on the next build.
- **"Last updated"** in the footers is set to the month of the latest build.
- **File versions.** The link to `style.css` gets a `?v=…` that changes whenever the file does, so after an update a returning visitor's browser never mixes an old page with new styles.

## Writing a post

1. Make a file in `posts/` named `YYYY-MM-DD-short-name.md`. The short name becomes the URL: `/blog/short-name/`.
2. Start it with a header, then write Markdown:
   ```
   ---
   title: My post
   date: 2026-11-02
   summary: One sentence for the lists, search results and link previews.
   ---
   ```
   Add `highlight: true` to put a post under the yellow highlighter in the lists, or `draft: true` to keep it unpublished.
3. Run `python build.py` (needs `pip install markdown` once).
4. Commit and push (see Publishing below). GitHub runs the build again when it publishes, so a post written on github.com works too.

Math works with `$inline$` and `$$display$$` (KaTeX, loaded only on posts that use it). Footnotes are `text[^1]` and then `[^1]: the note`. Fenced code blocks and tables work too.

Why a Python script and not Jekyll: Jekyll needs Ruby, which isn't installed here, so you couldn't preview posts before pushing them. Python is already here.

## Adding an experiment

1. Make `experiments/your-name/index.html`. Copying `experiments/index.html` gives you the page layout and the empty sidebar and meta markers; the archived logit lens in `../interp-archive/removed-samples/` is a full worked example.
2. Precompute the data into a `data.js` file next to it, so no model runs in the browser.
3. In `experiments/index.html`, replace "Nothing here yet" with the list in the comment below it. On the homepage, un-comment the Experiments section (it's just above Awards).
4. Run `python build.py` to fill in the sidebar and the link-preview tags, and to add the page to the sitemap.

## Compute spend

The box under the sidebar photo shows what you've spent on Vast.ai, RunPod and Modal. Every day at 09:00 UTC (and on every push) GitHub runs `spend.py`, which asks each provider's billing API for every month it still has and updates a month-by-month record in `compute.json`; `build.py` adds that up into the box. The box stays hidden until there's some spending, and in local previews (where there's no `compute.json`).

The record lives on the `data` branch, not on `main`, so the daily update never clashes with your pushes. Months a provider stops reporting (Modal keeps about a year) stay on the record, so it keeps the full history. To correct a month by hand (older spending, a provider with no API, or credits the API leaves out, like Modal grant credits), edit `compute.json` on the `data` branch on GitHub and put it under `"manual"`, e.g. `"manual": {"Modal": {"2026-10": 102.71}}`. A manual month replaces the fetched one and is never overwritten.

The API keys live in GitHub, not in the site: Settings > Secrets and variables > Actions, named `VAST` (or `VAST_API_KEY`), `RUNPOD` (or `RUNPOD_API_KEY`), and `MODAL` (both Modal tokens) or `MODAL_TOKEN_ID` plus `MODAL_TOKEN_SECRET`. Leave one out and that provider keeps its months as they are.

## Link previews and search

Each page's `<head>` has an empty `<!-- meta -->` block. `build.py` fills it from the page's `<title>` and `<meta name="description">`: the link-preview tags (what LinkedIn, Discord or iMessage show when someone shares the link, with your photo), the canonical address and the icons. So to change a page's preview, change its title or description and rebuild. New pages need the empty block too; copy it from any existing page.

The homepage also has a small block of structured data (`application/ld+json`) saying who you are, where you study and which GitHub and LinkedIn accounts are yours. Update it if those change.

After publishing, add the site in [Google Search Console](https://search.google.com/search-console) and submit `https://peterlurf.github.io/sitemap.xml`, so Google finds it within days instead of weeks.

## Previewing locally

```bash
python -m http.server 8040
```

Then open http://localhost:8040. Links like `/blog/` start at the site root, so opening the files directly from disk won't work; use the server.

## Publishing (free) with GitHub Pages

GitHub builds and publishes the site itself (`.github/workflows/deploy.yml`): every time a change reaches GitHub, it runs `build.py` and puts the result online about a minute later. It leaves out `options/` and `templates/`.

**Once:**
1. Install [GitHub Desktop](https://desktop.github.com) and sign in.
2. File > Add local repository > choose this folder. When it says it isn't a repository, click "create a repository" and name it exactly `PeterLurf.github.io`.
3. Click **Publish repository** and untick "Keep this code private".
4. On github.com, open the repository's **Settings > Pages**, and under "Build and deployment" set **Source** to **GitHub Actions**.
5. Watch the **Actions** tab: when the run turns green, the site is live at `https://peterlurf.github.io`.

Use GitHub Desktop for this first upload, not the web uploader: the web uploader can skip folders whose names start with a dot, like `.github`, and then nothing would build.

**After that, change things in either of two ways:**

- **On your computer:** edit, preview, then in GitHub Desktop write a short note, click **Commit**, then **Push**. Running `python build.py` first is still worth it so your local preview is right, but GitHub runs it anyway.
- **In the browser, from any computer or phone:** on github.com, open a file, click the pencil, edit, and click **Commit changes**. For a new post: open `posts/`, **Add file > Create new file**, name it `YYYY-MM-DD-short-name.md`, and paste in a header like the one above. No Python needed.

If you edit on github.com, click **Fetch origin** then **Pull** in GitHub Desktop before you next edit on your computer, so the two copies don't drift apart.

If a run fails (a red X in the Actions tab, and GitHub emails you), the live site stays as it was. Click the run to see the error; it's usually a typo in a post's header.

If you ever publish somewhere else, change `URL` at the top of `build.py` (it's used in the feed, the sitemap and link previews) and the addresses in `robots.txt` and the homepage's structured data.

The 404 page only works on the live site. The local preview server shows its own error page instead; open http://localhost:8040/404.html to see yours.
